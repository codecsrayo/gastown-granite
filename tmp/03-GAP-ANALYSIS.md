# Gap Analysis — What's Missing Between Current and Target

The gating document. If a gap is unfillable or its cost is
unaffordable, the migration plan stops here.

Each gap below has: what we have, what we need, what's missing, how to
fill, and a verdict on whether the fill is feasible with current
resources.

## G1. State event log — backing store

**Have:** `~/gt/.events.jsonl` (activity audit) via `internal/events/`.

**Need:** `<townRoot>/.beads/state-events.jsonl` (mutation log,
authoritative).

**Gap:**
- Separate file (cardinality + retention requirements differ from
  audit feed).
- Different schema (envelope with seq, target_db, schema_version).
- Different concurrency guarantees (need O_APPEND atomic; existing uses
  gofrs/flock which works but is heavier).

**Fill:**
- Extend `internal/events/` with `state/` sub-package.
- Mirror existing file-write pattern; swap flock for O_APPEND.
- Add rotation (daily) — none today.

**Cost:** ~1 week eng.

**Verdict:** 🟢 Fillable. Existing package gives proven template.

## G2. Producer API

**Have:**
- `internal/events.Event{}` envelope (audit-shaped).
- `events.RecordSling(...)` etc. — fire-and-forget helpers.
- No "wait for application" semantics anywhere.

**Need:**
- Typed `Producer` interface with `AppendAndWait`, `AppendAsync`,
  `WaitFor`, `WaitCaughtUp`.
- UNIX socket protocol between producer and materializer.
- Spool fallback when socket unavailable.

**Gap:**
- "Wait for ACK" semantics don't exist today.
- No UNIX socket transport.
- No spool directory pattern (though `~/gt/events/<channel>/` from
  channelevents is conceptually similar).

**Fill:**
- New `internal/events/state/producer/` package.
- UNIX socket: stdlib `net.Listen("unix", ...)`. Trivial.
- Spool: write to dir, materializer scans on startup. Atomic via
  rename.

**Cost:** ~1 week eng.

**Verdict:** 🟢 Fillable. Standard pattern.

## G3. Materializer daemon

**Have:**
- `internal/feed/` — tail-and-process daemon. Reusable pattern.
- `internal/daemon/` — daemon scaffolding (signal handling, lifecycle).
- `internal/checkpoint/` — distinct concept (session recovery), don't
  confuse.

**Need:**
- New daemon process.
- Per-event-type handler dispatch.
- Dolt transaction per event.
- Checkpoint per event (not batched) for crash safety.
- Dead-letter queue for poisoned events.
- Metrics/alerts.
- systemd unit + supervision.

**Gap:**
- Daemon doesn't exist.
- DLQ pattern doesn't exist in codebase.
- systemd integration: town boot uses its own supervisor pattern, not
  systemd. (`internal/boot/`, `internal/daemon/`). May need adapter.
- Test harness for materializer (real Dolt + injected events) doesn't
  exist.

**Fill:**
- New `internal/materializer/` package.
- New `cmd/beads-materializer/` binary.
- Integrate into town boot sequence.
- New `internal/testutil/MaterializerHarness`.

**Cost:** ~2-3 weeks eng (largest single chunk of work).

**Verdict:** 🟡 Fillable but the long pole. Operational debt is real.
Town doesn't currently run any per-host daemon at this criticality
level — adds a new "if this dies, everything stops" component.

## G4. Idempotency layer

**Have:** Nothing.

**Need:**
- Every event must apply at most once.
- Materializer must detect replay (crash, retry) and skip.
- Producer crashes between Append and Wait → potential duplicate; dedup
  by `trace_id`.

**Gap:**
- No `trace_id` concept in any current event/payload.
- No dedup state.

**Fill:**
- Add `trace_id` (ULID) to event envelope. Generated by producer.
- Materializer maintains a `seen_trace_ids` table in dolt (or a
  separate sqlite). Bounded by retention window (e.g. 7 days). Lookup
  on every apply.
- For mutation handlers: rely on dolt UNIQUE constraints + idempotent
  SQL where possible.

**Cost:** ~3 days eng.

**Verdict:** 🟢 Fillable. Pattern well-known.

## G5. Schema versioning

**Have:**
- bd has its own schema migrations (internal to bd).
- `internal/events/` has no version field; assumes single schema.

**Need:**
- Every event has `schema_version`.
- Materializer dispatcher selects handler by `(type, schema_version)`.
- Replay of historical events with old versions must produce same
  current dolt state.

**Gap:**
- Versioning doesn't exist.
- Test fixtures for cross-version replay don't exist.

**Fill:**
- Add `schema_version` field.
- Build handler matrix.
- Test suite that loads fixtures of every historical event version and
  replays.

**Cost:** ~1 week initial + ongoing maintenance per schema change.

**Verdict:** 🟡 Fillable but introduces permanent maintenance overhead.
Every event schema change becomes a multi-step process (add new
version, keep old handler).

## G6. Polecat producer integration

**Have:**
- Polecat uses TCP server mode for dolt.
- Polecat imports `internal/beads/` wrapper.
- 1 direct `exec.Command("bd", "update", ...)` in `session_manager.go`.

**Need:**
- Polecat lifecycle mutations (claim, hook, status change, release)
  flow through producer.
- High throughput path (`AppendAsync`) for bulk ops.

**Gap:**
- Polecats are managed by witness daemon (not us).
- Polecat session protocol is contract-stable; changing it requires
  polecat team buy-in.
- Some polecat ops are time-critical (heartbeats); event latency must
  stay <100ms or they crash.

**Fill:**
- Coordinate with polecat team (separate RFC).
- Phase 2 only after Phase 1 has been live + stable for >2 weeks.
- Provide fallback "direct write" flag for emergency rollback.

**Cost:** ~2 weeks eng + ~1 week polecat team coordination.

**Verdict:** 🟡 Fillable, but Phase 2 is the one-way door. Rollback
requires keeping dual-write infrastructure alive.

## G7. bd CLI upstream compatibility

**Have:**
- bd is upstream `steveyegge/beads@v1.0.4`.
- bd users (humans typing `bd close X` directly in terminals) exist.
- bd CLI is the documented interface in `AGENTS.md`.

**Need:**
- After migration, `bd close X` shouldn't write directly to dolt — it
  should emit an event.
- OR: bd remains as-is, and we provide a `gt bd` wrapper that emits
  events; AGENTS.md updated to use `gt bd ...`.
- OR: fork bd and patch its mutation paths.

**Gap:**
- We can't unilaterally change bd's behavior; upstream patches are
  slow (see hq-wt8 — filed locally, would need upstream PR).
- Forcing all users to `gt bd` instead of `bd` is a UX regression.
- Forking bd is a perpetual maintenance cost.

**Fill:**
- Recommended: wrap `bd` in `gt bd` and update AGENTS.md.
- Add a tap/hook that intercepts direct `bd <mutating>` invocations
  and routes through producer. Possible via PATH wrapper script.
- Lint rule that fails CI if AGENTS.md or any doc references bare `bd
  <mutating>` (not bare `bd show` etc).

**Cost:** ~1 week + ongoing AGENTS.md updates.

**Verdict:** 🟡 Workable but UX cost. PATH wrapper has its own race
risk (binary swap mid-call); requires careful design.

## G8. Cross-host coordination

**Have:**
- `issues.jsonl` committed in git. Push/pull merges state across hosts.
- Last-writer-wins via git merge.

**Need:**
- Either: per-host event logs, federated by git (status quo, just for
  events instead of jsonl).
- Or: centralized event log (out of scope per `01-CURRENT-STATE.md`
  section 8).

**Gap:**
- If we keep per-host event logs, cross-host conflicts shift from
  jsonl merges to event log merges. seq numbers won't align.
- Solutions: use ULID for ordering instead of seq; or per-host seq
  with host_id prefix.

**Fill:**
- Add `host_id` to event envelope. seq becomes `(host_id, seq)`.
- Materializer on host A still applies host A's events; host B
  similar. State eventually converges via git pull.

**Cost:** ~3 days eng.

**Verdict:** 🟢 Fillable, but introduces complexity that doesn't help
the original race problem. May be deferred until federation matters.

## G9. Audit/replay tooling

**Have:**
- `interactions.jsonl` (per-actor command history).
- `internal/events/` audit log.
- `internal/feed/` curator.

**Need:**
- `gt events list --since=X --type=Y` query.
- `gt events replay --to=<seq>` rebuild dolt to point-in-time.
- `gt events tail` live stream.

**Gap:**
- Query/replay tools don't exist.

**Fill:**
- New `internal/cmd/events.go` subcommand suite.
- Replay uses materializer in "replay mode" (no socket, deterministic).

**Cost:** ~1 week eng.

**Verdict:** 🟢 Fillable. Significant UX win once built.

## G10. Snapshot exporter (jsonl artifact)

**Have:**
- bd's auto-export (broken, throttled, racy — see PR 1).
- `bd export --all -o <file>` works manually.

**Need:**
- New `internal/snapshot/Exporter`: reads dolt, writes
  `<rig>/.beads/issues.jsonl` atomically, coordinated with materializer
  for consistent point-in-time.

**Gap:**
- Atomic write helper exists (`internal/atomicfile/`).
- Coordination with materializer (snapshot at seq N) doesn't exist.

**Fill:**
- New `internal/snapshot/` package.
- API: `snapshot.At(seq int64) (jsonlPath string, err error)`.
- Materializer exposes "current seq" endpoint; snapshot reads it,
  takes dolt snapshot, writes jsonl, names file with seq.

**Cost:** ~3 days eng.

**Verdict:** 🟢 Fillable.

## G11. Operational supervision

**Have:**
- Town uses internal supervisor (`internal/boot/`, `internal/daemon/`).
- Not systemd-based for the town processes.
- Some external services (Dolt) run in containers via docker-compose.

**Need:**
- Materializer supervised with restart-on-fail.
- Alerting when it falls behind or DLQ grows.
- Healthcheck endpoint for monitoring.

**Gap:**
- No existing alerting on per-host daemon health (beyond OTEL metrics).
- No pager/Slack integration for daemon failure.

**Fill:**
- Add OTEL metrics for materializer.
- Doctor check: `materializer-health`.
- Witness handler that publishes Slack alert on DLQ growth.

**Cost:** ~3 days eng + ongoing ops.

**Verdict:** 🟡 Fillable but ops debt. Without alerts, this becomes a
silent SPOF.

## G12. Observability — debugging an event-driven system

**Have:**
- OTEL tracing for some paths.
- `RecordBDCall` telemetry.
- No event-correlation tooling.

**Need:**
- Trace from CLI command → event → materializer apply → dolt commit,
  all under one trace_id.
- Dashboards: events/sec, materializer lag, DLQ depth, producer
  timeout rate.
- Debug command: `gt events trace <trace_id>` shows full timeline.

**Gap:**
- trace_id propagation across UNIX socket: need protocol field.
- OTEL span linking from producer → materializer.
- Dashboards don't exist.

**Fill:**
- Trace_id is in event envelope (G4); plumb through.
- OTEL spans on both sides; link by trace_id.
- Grafana dashboard (or whatever current OTEL backend renders).

**Cost:** ~1 week eng.

**Verdict:** 🟢 Fillable. Without it, debugging post-Phase 1 is
nightmare. Must land before Phase 1 ships.

## G13. Rollback strategy per phase

**Have:** Nothing formal. Each refactor lands or doesn't.

**Need:**
- Phase 0: trivially reversible (additive only).
- Phase 1: dual-write must remain alive for >2 weeks before flipping
  reads to materializer. Rollback = flip flag back to direct.
- Phase 2: polecats. ONE-WAY DOOR. Rollback requires re-implementing
  direct-write path in polecat, redeploying, and reconciling event
  log (events that happened during attempted rollback are stuck in
  log).
- Phase 3: external integrations. Easily disabled.
- Phase 4: cleanup. Removes safety net; only after months of
  stability.

**Gap:**
- No formal feature-flag system for state-event-driven mutations
  (other than per-package code branches).

**Fill:**
- Add `BEADS_USE_EVENTS=1` env var; producer checks. Default OFF in
  Phase 0, ON in Phase 1.
- Document rollback procedure for each phase.

**Cost:** ~1 day eng.

**Verdict:** 🟢 Fillable. Without this, Phase 1 is unsafe to ship.

## G14. Testing — divergence detection

**Have:** Unit tests, integration tests, subprocess policy tests.

**Need:**
- Divergence detector: run mutation through both paths (direct + via
  events), compare resulting dolt state. Fail CI on diff.
- Soak test: 24h continuous mutations + materializer running, assert
  zero data loss, zero divergence.
- Crash test: kill materializer mid-batch repeatedly, assert
  eventual consistency.

**Gap:**
- Detector doesn't exist.
- Soak harness doesn't exist (we have integration tests, not
  soak).
- Crash test scaffolding doesn't exist.

**Fill:**
- New `internal/testutil/DivergenceDetector`.
- New CI job: nightly soak (separate from PR CI).
- Crash test as Go test with subprocess kill.

**Cost:** ~1 week eng.

**Verdict:** 🟢 Fillable. Without it, Phase 1 ships blind.

## Showstoppers — gaps that COULD block the plan

| Gap | Showstopper if... |
|-----|-------------------|
| G3 materializer | Town runtime can't add a per-host daemon at this criticality (org policy or operational maturity not there yet) |
| G6 polecat coord | Polecats team unwilling to migrate; we'd be stuck with two write paths forever |
| G7 bd upstream | Users refuse to use `gt bd` instead of `bd`; PATH wrapper too fragile |
| G11 ops supervision | No on-call rotation that can respond to materializer down; silent SPOF unacceptable |

If any of the above are showstoppers, fall back to the lighter
alternative (server bus + PR 2) in `02-TARGET-ARCHITECTURE.md`
appendix.

## Recommendation from gap analysis

**Conditional GO:**
- Confirm operational supervision (G3, G11) with whoever owns town
  ops. If "we don't run daemons like that," STOP.
- Pre-discuss with polecats team (G6). If "no buy-in," STOP — would
  leave plan permanently incomplete.
- Confirm willingness to fork or wrap bd (G7). If "we must stay
  compat with bare bd," choose the gt-bd wrapper path; budget extra
  for PATH-wrapper edge cases.

If all three clear: GO. Plan in `05-MIGRATION-PHASES.md`.

If any blocks: take the lighter alternative. PR 1 (done) + PR 2
(1 day) + server bus (~1 sprint).
